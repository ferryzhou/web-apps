Ryan Lopopolo

Ryan Lopopolo leads a small team on OpenAI's Frontier group that built an internal product of over a million lines with no human-written code. His approach, harness engineering, puts the human effort into context, tools, tests and rules so Codex agents can write, review and merge the code.

Agent stories

An internal product built with zero human-written code

  • built a feature
  • About 1M lines and about 1,500 PRs in five months

Starting in mid-2025 from an empty repo, a team of three engineers banned hand-written code and had Codex build an internal product. It passed a million lines across roughly 1,500 PRs in about five months.

Details
  • Setup: three engineers at first, later about seven; the rule was that no human types production code.
  • Codex wrote the app, tests, docs and tooling; humans built the harness and reviewed plans.
  • The first six weeks or so were about 10 times slower than doing it by hand.
  • Result: a working Electron app used internally, with no human-written lines.

The team averaged about 3.5 PRs per engineer per day in late 2025. After newer Codex models arrived, Ryan reports 5 to 10 a day and about 70 a week, which he calls more than linear scaling.

Details
  • Late December 2025: about 3.5 PRs per engineer per day.
  • After GPT-5.2 in January 2026: 5 to 10 PRs per engineer per day.
  • By June 2026 he cites about 70 PRs per engineer per week.
  • He says new hires made the team faster within two weeks because Codex was the single entry point to the codebase.

One timeout bug became a rule for all future code

  • solved a problem

A Slack report about a missing network timeout led to a point fix and an update to the repo's reliability doc. Every later agent run now follows the rule that network calls need timeouts.

Details
  • Trigger: a reliability problem raised in Slack.
  • An agent made the fix in the affected code.
  • The team updated the reliability doc the agents read, so the rule applies to all future work.
  • Lint and test errors are written to tell the agent how to fix the problem.

A PM's markdown PRD became a live feature in a week

  • built a feature
  • Live within the same week

A PM wrote a markdown PRD for a skills system in the app. The team reviewed it once in a weekly meeting, and agents had the feature live by the end of the week.

Details
  • Setup: the PRD lived in the repo, next to docs, tests and harness rules.
  • Humans reviewed the plan once instead of reviewing code line by line.
  • Codex agents implemented, reviewed and merged the work.
  • Ryan says PMs on the team have shipped about 100K lines of production code this way.

Symphony runs one supervised agent per task

  • built a feature

The team built Symphony, an Elixir orchestration layer that starts a supervised process for each task. A rework state throws away a failed attempt and restarts it, and agents attach a proof-of-work video to each PR.

Details
  • Each task gets its own supervised process and worktree.
  • A land skill has Codex push the PR, wait for CI and review, fix flaky tests and merge.
  • Rework discards the worktree and restarts, so the team can study what the agent got wrong.
  • Status: internal only as of April 2026, with no external customers yet.

Key learnings

  • When an agent fails, ask what context or tool it is missing before prompting harder.
  • Keep AGENTS.md short, about 100 lines, as a table of contents into deeper docs.
  • Keep the inner build loop under a minute; split the build graph when it slips.
  • Encode every repeated piece of feedback or incident as a doc rule, lint or test, and hold a weekly cleanup pass for drift.
  • Let agents run the whole PR loop, tune review agents to favor merging, and move most human review to plans and post-merge samples.
  • Prefer small CLI tools with terse output over MCP connections for agent tooling.
  • Spend tokens freely and treat code as disposable; he calls using less than a billion tokens a day borderline negligent. His throughput numbers and his share of time spent writing code (down to about 30%) shifted as models improved between April and June.

Interview notes

Ryan Lopopolo: Shipping a Product with Zero Human-Written Code

Ryan Lopopolo of OpenAI on AI Native Dev (Jun 2026), with more detail on Latent Space (Apr 2026). His team of 3, later 7, engineers built an internal app with more than 1M lines of code. Agents wrote all of it. Each engineer now ships about 70 PRs a week. The first six weeks were 10 times slower than writing the code by hand.

Practices

  • When the agent fails, ask what context or tool it's missing. Don't just prompt harder.
  • Keep builds under a minute so agents stay fast.
  • Keep AGENTS.md to about 100 lines. Use it as a table of contents for deeper docs: goals, customers, quality bar.
  • Turn every incident into a written rule, such as "all network calls need timeouts." Write lint and test errors for the agent, telling it how to fix the problem.
  • Tell review agents to bias toward merging and flag only important issues. Otherwise author and reviewer loop forever.
  • Let agents run the whole PR: push, wait for CI, fix flaky tests, resolve conflicts, merge.
  • Do most human review after merge, on samples. Review the plans before work starts.
  • Hold a weekly cleanup day. Encode repeated feedback so you never give it twice.
  • Prefer small command-line tools with terse output over MCP.
  • Treat code as disposable. He'll throw away a 50,000-line experiment to learn where agents struggle.

Lessons

  • "The only fundamentally scarce thing is the synchronous human attention of my team."
  • Humans still own hard refactors, new product ideas, interfaces and customer conversations.
  • Caveat: this was a brand-new codebase.
